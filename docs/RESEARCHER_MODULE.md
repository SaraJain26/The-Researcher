# The Researcher Module

## Overview

`The Researcher` is the evidence-gathering and case-enrichment agent in the autonomous financial crime investigation system.

Its job is not to detect fraud from scratch. That responsibility belongs to `The Sentry`.

Instead, `The Researcher` takes a suspicious case produced by `The Sentry`, gathers all relevant contextual evidence from structured systems and internal services, and produces a single investigation dossier that downstream agents can use.

In the full multi-agent pipeline:

- `The Sentry` detects suspicious behavior
- `The Researcher` gathers supporting evidence
- `The Compliance Officer` maps evidence to AML/BSA or policy rules
- `The Scribe` drafts the final narrative or SAR
- `The Orchestrator` coordinates the flow

## Core Responsibility

The Researcher answers:

- Who is this customer?
- What exactly happened in the flagged transaction?
- Is the IP behavior suspicious?
- Is the device linked to other risky entities?
- Are there shared identifiers across multiple customers?
- Has this customer been investigated before?

Its output is a structured, audit-friendly JSON case dossier.

- `decision_support`

## How It Works

At a high level, The Researcher follows this sequence:

1. Receive a Sentry alert
2. Extract key identifiers from the alert
3. Query structured SQL data sources
4. Call internal API connectors for enrichment
5. Correlate the evidence
6. Score the evidence and recommend an action
7. Return a structured investigation dossier

## Data Sources Used

In this hackathon version, The Researcher uses a hybrid setup.

### 1. Structured SQL Data

The SQL layer acts like the bank's operational systems and stores:

- customer profiles
- onboarding documents
- accounts
- transactions
- login history
- device details
- entity links
- prior cases

In this project, these are stored in a synthetic SQLite database generated by:

- [generate_synthetic_data.py](C:\Users\sara\OneDrive\Desktop\The Researcher\generate_synthetic_data.py)

### 2. Internal API Connectors

The API connector layer simulates internal services that would normally exist inside a bank, such as:

- case annotation services
- IP intelligence services
- device risk services

In this project:

- the fake internal APIs are served by [internal_api_server.py](C:\Users\sara\OneDrive\Desktop\The Researcher\internal_api_server.py)
- the seed responses come from [sample_data/internal_api_data.json](C:\Users\sara\OneDrive\Desktop\The Researcher\sample_data\internal_api_data.json)
- the client connector used by The Researcher is implemented in [researcher_agent.py](C:\Users\sara\OneDrive\Desktop\The Researcher\researcher_agent.py)

### 3. Optional External API Enrichment

The hybrid version also supports optional external IP enrichment.

This lets the project use one real external API for IP geolocation or reputation while keeping the rest of the demo synthetic and stable.

If no external API is configured, The Researcher falls back to the internal mock IP intelligence response.

## Internal Flow In Detail

### Step 1. Read The Sentry Alert

The Researcher starts with a suspicious case, typically from:

- [sample_data/sample_sentry_alert.json](C:\Users\sara\OneDrive\Desktop\The Researcher\sample_data\sample_sentry_alert.json)

This provides the initial case context.

### Step 2. Query SQL Tools

Using the IDs from the alert, The Researcher looks up:

- the customer record
- the flagged transaction
- associated accounts
- login history
- device metadata
- linked entities
- prior investigations

This is the structured evidence layer.

### Step 3. Call API Connectors

The Researcher then fetches enrichment from internal services:

- case annotations
- IP intelligence
- device graph/risk signals

These calls are made through connector classes in:

- [researcher_agent.py](C:\Users\sara\OneDrive\Desktop\The Researcher\researcher_agent.py)

### Step 4. Correlate Signals

The Researcher merges the SQL and API data to detect meaningful case patterns such as:

- IP-country mismatch
- impossible travel
- VPN or proxy usage
- shared device across accounts
- shared email or phone across customers
- prior investigations for the same customer

### Step 5. Build Research Summary

After collecting evidence, The Researcher writes a short summary of the most important findings.

Examples:

- login from different countries in a short time window
- device linked to multiple accounts
- prior monitoring history
- risky cross-border transfer behavior

### Step 6. Produce Decision Support

The Researcher does not make the final regulatory decision, but it helps downstream agents by providing:

- evidence score
- reason codes
- recommended action such as `clear_with_note`, `monitor`, or `escalate`
- missing information flags

## Why This Is Not Pure RAG

The Researcher is primarily a retrieval and enrichment module.

It retrieves structured evidence from SQL and APIs, but it does not yet perform classic document-based RAG with:

- embeddings
- vector search
- chunk retrieval
- LLM-generated answers from unstructured document context

So the best description is:

- retrieval layer
- evidence enrichment module
- structured context builder

In a full multi-agent RAG system:

- The Researcher provides retrieval and enrichment
- The Compliance Officer can use regulatory RAG
- The Scribe can use LLM generation for narratives

## Why This Design Is Good For A Hackathon

This architecture is strong for a hackathon because it is:

- realistic enough to resemble enterprise systems
- stable enough to demo reliably
- modular enough to extend later
- easy to explain to judges

It also gives a strong production story:

- SQLite can later be replaced by PostgreSQL or warehouse tables
- fake internal APIs can later be replaced by real services
- optional external enrichment can later become live integrations
